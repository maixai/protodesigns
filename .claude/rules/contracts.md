# contracts:契约书写与跨端一致性规则

本文件规定**契约怎么写**、**生成物怎么用**、以及**哪些东西必须跨端一致、哪些允许不同**。

## ① 契约是什么

`contracts/main.tsp` 是**"数据长什么样"的单一事实源**。各端类型由 `make contracts` 生成,`src/api/` 等处的类型**必须来自生成物**。

```text
contracts/main.tsp ──tsp compile──┬─→ contracts/generated/openapi/openapi.yaml
                                   └─→ contracts/generated/schema/*.yaml
                                            ├─→ src/contracts/generated/*.d.ts   (web / 桌面)
                                            └─→ lib/contracts/generated/*.dart   (mobile)
```

| 目录 | 性质 |
| --- | --- |
| `contracts/main.tsp` | **手写**(源头) |
| `contracts/generated/` | 生成物,勿手改,不入库 |
| `src/contracts/generated/`、`lib/contracts/generated/` | 生成物,勿手改,不入库 |

## ② 书写约定(踩过的坑,务必遵守)

1. **入口类型加两个标注**:

   ```typespec
   @summary("User")
   @jsonSchema
   model User { ... }
   ```

   - `@jsonSchema` 是产出的前提,不加则 emitter 什么都不生成;
   - `@summary("User")` 决定**生成的类型名**。不加会退化成从文件名派生的名字(如 `UserYaml`)。

2. **被引用的类型不加标注**:枚举 / 标量被入口类型引用时,会自动内联进该 schema,因此每个生成的 schema 文件都是**自包含**的,不会产生跨文件的重复导出。

3. **一个"入口类型"对应一个文件** —— 需要独立产出的实体才加标注;不要给每个小类型都加,否则会产生大量碎片文件。

4. **改了契约必须重新生成**:生成物不入库,新克隆的目录靠 `make run` 自动生成。

### Dart 侧(Flutter)的保真度取舍

TypeSpec **官方没有 Dart emitter**(官方只提供 JS / Python / C# / Java),故 Dart 侧走 `quicktype`,把 JSON Schema 转成带 `fromJson` / `toJson` 的 Dart 类。实测已知两处取舍:

| 现象 | 说明 | 应对 |
| --- | --- | --- |
| 枚举**以字段名命名** | 契约里的 `UserRole` 在 Dart 侧生成的是 `enum Role`(取自字段名 `role`),不是 `UserRole` | 每个生成文件自包含,只要不在同一文件里 import 两份生成物就不会冲突;**若两个模型都有 `role` 字段且需同时引用,需手工改名** |
| 枚举值为**全大写** | `admin` → `Role.ADMIN` | 展示时按需转换(如 `.name.toLowerCase()`) |
| 自定义 scalar **被内联** | 契约里的 `ItemId` 在 Dart 侧变成裸 `String`,语义丢失 | 靠命名约定保留语义;不要依赖 Dart 侧的类型区分 |

生成的 Dart 文件不参与 lint(已在 `analysis_options.yaml` 的 exclude 中排除),其风格由 quicktype 决定,不要手改。

## ③ `data` 字段决定契约形态

| `data` 取值 | 契约侧重 | 说明 |
| --- | --- | --- |
| `remote-http` | 接口契约(OpenAPI) | 有明确的服务端接口,`tspconfig.yaml` 的 openapi3 emitter 是主线 |
| `local-first` | 数据模型契约 | 数据主要存本机,重点是实体结构与同步规则,而不是 HTTP 端点 |
| `hybrid` | 两者都要 | 需分别定义数据模型与同步接口 |

**`data` 必填,不设默认值** —— 两种形态差别很大(是否要生成数据库结构、是否要设计同步规则),猜错方向会导致整套设计返工。

## ④ 跨端一致性规则

### 必须跨端一致

以下内容在所有端上**必须完全一致**,不一致即判 fail:

| 项 | 说明 |
| --- | --- |
| 信息架构 | 页面 / 模块的划分与层级 |
| 数据契约 | 实体、字段、取值集合(枚举) |
| 文案 | 同一功能的名称与提示语 |
| 状态机 | 同一流程的状态与流转(如订单状态) |
| 业务规则 | 校验规则、权限判定 |

### 允许不同(甚至应当不同)

| 项 | 说明 |
| --- | --- |
| 导航形态 | 桌面用侧栏 / 菜单栏,移动用底部 Tab |
| 版式 | 桌面多栏,移动单栏 |
| 控件外观 | 各平台的原生控件风格 |
| 交互手势 | 移动的滑动返回等 |
| 信息密度 | 桌面可密,移动宜疏 |

> 判据:**"用户看到的事实"必须一致,"用户怎么操作"允许按平台最自然的方式来做。**

### 一致性的保障方式

- **机制层**:`product` 字段相同的原型,其契约应保持一致 —— 契约的书写与核对由本规则约束。
- **人工层**:交接给开发前,**必须**逐项核对同 `product` 的各原型之间的契约是否一致。
- 目前**没有**自动核对工具(刻意不做,避免过度工程);当同产品的多端原型积累到一定数量后再评估是否需要。

## ⑤ 交付给开发时,契约怎么交接

契约是**交接物**的一部分,与原型代码、端基线一起流出:

- 开发方拿到的是"接口形状的权威定义",而不是散落在组件里的类型;
- 若开发期需要调整契约,应回到原型仓库改 `main.tsp` 后重新生成,而不是在开发仓库里手改类型。
